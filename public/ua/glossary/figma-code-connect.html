Figma Code Connect

Дизайн-системи та інженерія • ШІ та агентні системи

Figma Code Connect пов'язує компоненти в бібліотеці дизайну Figma з їхніми реалізаціями в кодовій базі. Ці зв'язки допомагають розробникам та ШІ-агентам знаходити реальний код, асоційований із дизайн-компонентом.

Що саме додає Code Connect?

Дизайн-компонент і компонент у коді можуть мати різні назви, значення властивостей та правила композиції. Зв'язок фіксує, як саме вони співвідносяться між собою, замість того щоб змушувати розробника чи ШІ здогадуватися про реалізацію за візуальним виглядом.

Наприклад, кнопка у Figma може мати властивість Size зі значенням Large, тоді як API коду приймає size="large". Мапінг цієї відповідності значно полегшує отримання правильної кодової реалізації.

Такий зв'язок є посиланням на знання про реалізацію. Проте він сам по собі не гарантує, що кожен екран, який використовує цей компонент, працюватиме коректно.

Інтерфейс Code Connect проти CLI

Figma надає графічний інтерфейс (UI) для зв'язування компонентів дизайну з реалізаціями в репозиторії, а також інтерфейс командного рядка (CLI) для публікації зв'язків та прикладів коду. Рекомендований шаблонний підхід у CLI дозволяє командам точно контролювати фрагменти коду (snippets) і зіставлення властивостей, які вони надають.

Ці інтерфейси передбачають різні робочі процеси редагування та конфігурації. Ознайомтеся з актуальним порівнянням і вимогами до доступу у Figma перед вибором підходу. Не варто припускати, що будь-який спосіб зв'язування створює абсолютно однаковий досвід роботи з фрагментами коду в режимі розробника (Dev Mode).

Як це співвідноситься із сервером Figma MCP?

MCP-сервер Figma передає контекст дизайну підключеному агенту. Code Connect може збагачувати цей контекст прямими посиланнями на фактичні компоненти в кодовій базі.

Вони вирішують взаємопов'язані завдання: MCP надає інтерфейс для отримання та використання контексту, а Code Connect встановлює конкретні мапінги між дизайном і кодом. При цьому жоден із них не замінює рекомендацій щодо використання компонентів або бізнес-правил самого застосунку.

Приклад: кнопка дії бронювання

Припустимо, команда зіставляє свій компонент BookingButton у Figma зі спільним компонентом у коді. Мапінг визначає шлях імпорту, а також підтримувані параметри розміру та акценту (emphasis). Робочий приклад демонструє стан очікування (pending state).

Проте завдання з імплементації все одно вимагає визначення: коли саме починається запит на бронювання, як обробляється повторне відправлення форми та що відбувається в разі помилки. Ці рішення належать до логіки продуктового процесу та відповідної документації.

Перевіряйте згенероване використання компонента на відповідність його реальному API, а потім обов'язково тестуйте супутню взаємодію.

Що повинні підтримувати команди?

Оновлюйте мапінги у разі зміни ідентифікаторів компонентів, шляхів імпорту або підтримуваних пропсів. Звіряйте показові інстанси з дизайну з актуальною випущеною реалізацією в коді. Призначайте відповідального за невирішені зв'язки замість того, щоб сприймати їх як успішно встановлені.

Зберігайте інформацію про версії та налаштування доступу в документації проєкту. Ставтеся до мапінгу як до регулярного процесу підтримки зв'язку з реалізацією та тестуйте отриману поведінку безпосередньо в продукті.
