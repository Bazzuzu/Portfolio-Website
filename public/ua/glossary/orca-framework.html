Фреймворк ORCA

UX та архітектура продукту • Продуктова стратегія та зростання

Фреймворк ORCA — це методологія Софії Пратер для практичного застосування об'єктно-орієнтованого UX (OOUX). Абревіатура ORCA розшифровується як Objects, Relationships, Calls to action (CTAs) та Attributes (об'єкти, зв'язки, заклики до дії та атрибути). Команди використовують його для трансформації результатів досліджень користувачів у цілісну модель об'єктів продукту, їхніх взаємозв'язків, доступних дій та інформаційного наповнення.

Object-Oriented UX provides the design principles. ORCA provides activities for defining the model and using it to design and test interfaces.

What does ORCA stand for?

Consider one illustrative object in a support tool, Ticket #1042 about a missing invoice.

ORCA element Ticket example
Object Ticket is the object type. Ticket #1042 is one instance.
Relationships Linked customer — Acme Studio. Assigned agent — none.
Calls to action A supervisor can reopen the ticket after selecting an agent.
Attributes Subject — Missing invoice. Status — Closed. Priority — Normal.

Customer and Agent are objects with their own records. The ticket links to those records through relationships. Status and priority describe the ticket as attributes.

How does the ORCA process work?

ORCA works through four iterative rounds. Teams revisit and refine Objects, Relationships, Calls to action, and Attributes as the model develops.

  1. Discovery. Identify objects from research. Map their relationships, record actions by object and role in a CTA Matrix, and build an initial object map. Capture questions for further research.
  2. Requirements. Define relationship rules, permissions, and required fields. Document object definitions in an Object Guide and expand the CTA matrix into object-oriented user stories. Clarify the rules for the object's attributes.
  3. Prioritization. Decide what belongs in the release and which information and actions deserve prominence in the interface.
  4. Representation. Turn the model into cards, lists, detail views, and a connected prototype. Use a Shapeshifter Matrix to examine intentional variants. Test whether users recognize the objects, find their connections, and understand the available actions.

This sequence provides a starting point. The rounds can be adapted to the project. Prater describes moving Prioritization ahead of detailed Requirements when time is limited. Prioritizing Prioritization for Product Designers, Sophia Prater

An ORCA example in practice

For Ticket #1042, the reopening rule connects a user role, the ticket’s status, and its relationship to an agent. These requirements guide who sees the action, when it is available, and what information is needed to complete it.

The team can prototype the ticket view to test whether supervisors can find the action and understand why they need to assign an agent.

When should you use ORCA?

Use ORCA when a team needs to agree on connected objects, role permissions, or business rules before designing screens. Start with one object and a real task. Check the model with users and domain experts, and return to research wherever important questions remain unanswered.
