Фреймворк ORCA

UX та архітектура продукту • Продуктова стратегія та зростання

Фреймворк ORCA — це методологія Софії Пратер для практичного застосування об'єктно-орієнтованого UX (OOUX). Абревіатура ORCA розшифровується як Objects (об'єкти), Relationships (зв'язки), Calls to action (заклики до дії, CTA) та Attributes (атрибути). Команди використовують його для перетворення результатів користувацьких досліджень на структуровану модель об'єктів продукту, їхніх зв'язків, доступних дій та інформаційного наповнення.

Об'єктно-орієнтований UX (OOUX) закладає фундаментальні принципи проєктування. ORCA пропонує практичні активності для формування цієї моделі та її подальшого використання під час проєктування й тестування інтерфейсів.

Що означає абревіатура ORCA?

Розглянемо як ілюстрацію конкретний об'єкт у системі підтримки: тікет №1042 щодо відсутнього інвойсу.

Елемент ORCA Приклад для тікета
Об'єкт Тікет (Ticket) — це тип об'єкта. Тікет №1042 — один із його екземплярів.
Зв'язки Пов'язаний клієнт — Acme Studio. Призначений оператор — відсутній.
Заклики до дії Супервайзер може повторно відкрити тікет після вибору оператора.
Атрибути Тема — Відсутній інвойс. Статус — Закритий. Пріоритет — Звичайний.

Клієнт (Customer) та Оператор (Agent) є об'єктами з власними записами. Тікет посилається на ці записи через зв'язки. Статус і пріоритет описують тікет як атрибути.

Як влаштований процес ORCA?

Процес ORCA розгортається у чотири ітеративні раунди. Команди послідовно повертаються до об'єктів, зв'язків, закликів до дії та атрибутів, удосконалюючи модель у міру її розвитку.

  1. Дослідження (Discovery). Визначення об'єктів на основі досліджень. Складання карти зв'язків, фіксація дій за об'єктами та ролями в матриці CTA (CTA Matrix) та побудова початкової карти об'єктів. Фіксація відкритих питань для подальших досліджень.
  2. Вимоги (Requirements). Визначення правил зв'язків, прав доступу та обов'язкових полів. Документування визначень об'єктів у картці об'єкта (Object Guide) і розширення матриці CTA в об'єктно-орієнтовані історії користувачів. Уточнення правил для атрибутів об'єкта.
  3. Пріоритезація (Prioritization). Ухвалення рішень щодо того, що увійде до релізу, та яка інформація й дії заслуговують на найбільшу помітність в інтерфейсі.
  4. Репрезентація (Representation). Трансформація моделі в картки, списки, детальні перегляди та інтерактивний пов'язаний прототип. Використання матриці трансформації станів (Shapeshifter Matrix) для опрацювання цілеспрямованих варіантів відображення. Тестування того, чи впізнають користувачі об'єкти, чи знаходять зв'язки між ними та чи розуміють доступні дії.

Ця послідовність є відправною точкою. Раунди можна адаптувати під потреби проєкту. Пратер описує перенесення раунду пріоритезації перед етапом детальних вимог у разі обмеженого часу. Пріоритезація пріоритезації для продуктових дизайнерів, Софія Пратер

Приклад використання ORCA на практиці

Для тікета №1042 правило повторного відкриття пов'язує роль користувача, статус тікета та його зв'язок із оператором. Ці вимоги визначають, хто бачить дію, коли вона доступна та яка інформація потрібна для її завершення.

Команда може створити прототип екрана тікета, щоб перевірити, чи можуть супервайзери легко знайти цю дію та чи розуміють вони, чому спершу необхідно призначити оператора.

Коли слід використовувати ORCA?

Використовуйте ORCA, коли команді необхідно узгодити взаємопов'язані об'єкти, права доступу для різних ролей або бізнес-правила ще до початку проєктування екранів. Почніть з одного об'єкта та реального робочого завдання. Перевірте модель разом із користувачами та експертами предметної області й повертайтеся до досліджень щоразу, коли важливі питання залишаються без відповіді.
