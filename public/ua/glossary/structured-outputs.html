Структуровані виводи (Structured Outputs)

ШІ та агентні системи

Структуровані виводи (Structured outputs) — це відповіді моделі, суворо обмежені заданим форматом або схемою (schema). Вони дозволяють додатку запитувати чітко визначені поля та типи даних, такі як ідентифікатор бронювання та статус, замість парсингу та інтерпретації довільної текстової відповіді.

Що саме контролює схема?

Схема описує властивості, обов'язкові поля, типи даних та перелік дозволених значень (enum). Безпосередньо API моделі визначає, які саме можливості схем воно підтримує та гарантовано забезпечує на рівні генерації.

Наприклад, додатку може бути потрібне рядкове поле reservation_id та поле status, вибране серед значень confirmed, canceled або unknown. Можлива відповідь:

{
  "reservation_id": "R-104",
  "status": "unknown"
}

Це лише ілюстративні дані додатку, а не доказ того, що бронювання R-104 дійсно існує. Схема контролює виключно синтаксичну структуру відповіді. Додатку все одно необхідно самостійно перевірити наявність запису, джерело даних та його актуальний статус.

Структуровані виводи, режим JSON та виклик інструментів

Механізм Основне призначення
Режим JSON (JSON mode) Запит синтаксично коректного JSON без жорсткої фіксації схеми полів, залежно від поведінки API
Структуровані виводи (Structured outputs) Суворе обмеження відповіді за допомогою підтримуваної схеми (наприклад, JSON Schema)
Виклик інструментів або функцій (Tool / Function calling) Надання моделі можливості ініціювати операцію, визначену додатком, передаючи аргументи

Ці механізми можна комбінувати в межах одного робочого процесу. Згенерований моделлю аргумент інструмента залишається вхідними даними, які обов'язково потребують валідації, а не автоматичним дозволом на виконання операції.

Структуровані дані для LLM (Structured Data for LLMs) — це окрема тема, яка стосується публікації машинозчитуваної інформації про контент вебсторінок, наприклад розмітки Schema.org у форматі JSON-LD.

Приклад: перетворення листа на форму перевірки

Операційний інструмент вилучає ім'я пасажира та бажану дату подорожі з тексту електронного листа. Відповідь використовує чітко визначені поля та явно фіксує відсутні відомості.

Інтерфейс відображає оригінальний фрагмент тексту поруч із кожним вилученим значенням. Оператор може відкоригувати форму перед її збереженням. Сервер окремо й незалежно перевіряє формати, права власності на запис та діючі бізнес-правила.

Дата може бути коректним рядком формату ISO, але водночас бути помилковою для даного бронювання. Крім того, відповідь, що повністю задовольняє схему, може опустити важливе застереження чи контекст із тексту листа.

Що необхідно специфікувати дизайнерам та архітекторам?

Проєктуйте інтерфейси з розрахунком на відсутні значення, непідтримувані запити, відмови моделі від генерації (refusals), неповні відповіді та збої валідації. Чітко визначте, які значення можна застосовувати автоматично, які потребують підтвердження людиною, а що користувачі можуть переглянути чи відредагувати.

Тестуйте семантичну точність і зміст, а не лише відповідність формату. Включайте неоднозначний вихідний текст і суперечливі записи до тестового набору (evaluation set). Високий відсоток проходження схеми (schema-pass rate) сам по собі майже нічого не говорить про те, чи отримують користувачі коректну та достовірну інформацію.
